# Административная лента решений — хранение и доставка через YugabyteDB

## Решение

Источником истины для новых записей административной ленты является **YugabyteDB YSQL**, а не Redis Pub/Sub и не память процесса ASP.NET. Каждому типу решения соответствует микросервис-владелец:

| Ответственный API | Виды работ | Таблица событий |
| --- | --- | --- |
| `tasks-api` | тесты, математика | `taskforge_k3s_tasks.AdminSolutionFeedEvents` |
| `solutions-api` | код, SQL, изображения | `taskforge_k3s_solutions.AdminSolutionFeedEvents` |

Каждое новое решение/отправленная попытка и запись события добавляются **в одной транзакции `SaveChanges`**. Код и SQL затем создают новое событие при итоговом вердикте; кодовые случаи `ExecuteUpdateAsync` с вердиктом об ошибке обёрнуты в явную транзакцию с записью события. Уже открытые попытки тестов и математики не появляются в ленте до отправки.

События содержат ID, тип работы, пользователя, задание, статус, процент и время, но **не содержат исходный код или ответы учащихся**. Подробности загружаются только отдельным защищённым административным API. При удалении аккаунта события данного пользователя также удаляются; при объединении аккаунтов идентификаторы в ленте переносятся на целевой аккаунт.

## Поток браузеру

- `GET /api/admin/solution-events` — `solutions-api`: код, SQL, изображения.
- `GET /api/admin/task-solution-events` — `tasks-api`: тесты и математика.
- Оба защищены проверкой роли **Admin**. Nginx в изолированном K3s направляет запросы каждому владельцу.
- Фронтенд открывает **два независимых `EventSource`** с cookies. Если один источник недоступен, интерфейс не показывает ложный статус «В эфире».
- Каждый API опрашивает **собственную** таблицу YugabyteDB раз в **1 секунду** и отправляет новое событие через SSE. Нет межрегионального Redis Pub/Sub и общих таблиц другого сервиса.
- При обычном открытии отдаётся до **100 последних событий каждого источника**; после сетевого разрыва браузер автоматически пересылает SSE `Last-Event-ID`, и сервис читает пропущенные события из базы. Дополнительно перекрываются 45 секунд времени событий для поздних фиксаций транзакций; одинаковые события на фронтенде сворачиваются в одну карточку решения.
- Модель в интерфейсе ограничивает число видимых карточек **120**, но это не ограничение хранения в YugabyteDB. При обновлении вкладки возвращаются последние события; полная история старых работ доступна в существующих административных списках решений.
- Для первых карточек отображаются вид решения, ID пользователя и статус; имена и детали подгружаются в фоне, максимум 6 параллельных обогащений.

## Межрегиональный сценарий

Ученик отправляет решение через API в Беларуси → транзакция подтверждена общей YugabyteDB → API в Польше на следующем цикле чтения обнаруживает событие → передаёт карточку через локальное SSE-соединение администратору.

**Это не гарантированная доставка за 1 секунду.** До отображения добавляются время распределённого COMMIT, реальный RTT, очередь запросов и задержка SSE. При недоступной общей YugabyteDB лента не может обновляться, но уже подтверждённые события не исчезают из-за перезапуска отдельного API.

Текущая K3s-сборка — отдельный одноузловой лабораторный профиль с **YugabyteDB RF1**. Реальная геораспределённая конфигурация **RF3 не развернута и не проверена**. У регионов должна быть одна согласованная YugabyteDB, а не независимые YSQL-кластеры; сценарий с разными непересекающимися базами не поддерживается.

## Миграции и публикация

Новые схемы вводятся EF Core миграциями `20261119090000_AdminSolutionFeedOutbox` отдельно для `tasks` и `solutions`. При первом деплое **сначала** применить миграции двух сервисов и только потом запускать новые API. CI применяет миграции перед публикацией образов; реальный прогон на YugabyteDB после этих изменений должен подтвердить следующий GitHub Actions run.

Миграция не переписывает историю уже существовавших решений в новую таблицу. Их можно посмотреть в обычных исторических API, но лента SSE начинает накапливаться с первого нового события после обновления.

## Что удалено / что сохранено

Удалены механизм списка редакторов карты, временные ключи присутствия в Redis, heartbeat, API-хаб `CourseMapPresenceHub` и визуальные индикаторы онлайна. **Сохранены** проверки версии карты и событие `MapSaved`: это не список людей онлайн, а уведомление о чужом сохранении; в двух регионах с раздельным Redis оно может не передаваться, но `409 Conflict` защищает содержимое от тихого перезаписывания.

Minecraft-чат **не менялся**. Интерактивный компилятор **не менялся**, его отдельный реворк в рамках этой работы не выполнялся. Анализатор аккаунтов сохранён.

## Границы надёжности

События записываются атомарно с основными решениями; это решает потерю между COMMIT и Redis publish. SSE может **повторить** события после переподключения — клиент должен быть идемпотентен. При очень длительном разрыве и повторном открытии вкладки загрузятся до 100 последних записей каждого источника, не вся бесконечная история. Для произвольной исторической навигации используйте существующие списки решений.

SSE использует окно позднего COMMIT 45 секунд. Для сколь угодно длительных межрегиональных транзакций и строгого глобального total-order потребуется отдельный упорядоченный журнал с курсором на уровне БД; данный вариант не обещает этого. Контракты, синтаксис и фронтенд-тесты проверяются локально; полный C# build и живой K3s/YSQL smoke доступны только там, где установлен .NET 10 и YugabyteDB (GitHub Actions).
