# Аудит и реворк архитектуры фронтенда TaskForge

## Что было сломано архитектурно

Раньше почти каждая страница сама импортировала и монтировала `Layout`:

```jsx
<Layout>
  <Page />
</Layout>
```

При переходе на другой маршрут React Router удалял старую страницу вместе с `Layout` и создавал новый `Layout`. Из-за этого обычная навигация уничтожала и запускала заново:

- Canvas/WebGL-фон;
- шапку и боковую навигацию;
- мобильное меню;
- `QuotaProvider` и данные энергии;
- секундные таймеры;
- слушатели настроек и событий;
- часть состояния интерфейса.

Это было именно перемонтирование, а не безобидный повторный вызов render-функции. Поэтому фон перезапускался, случайный эффект мог меняться, а энергия сначала становилась `null`, исчезала и появлялась только после нового HTTP-запроса.

## Новое дерево приложения

Главный фронтенд теперь построен так:

```text
BrowserRouter
└── AppProviders
    ├── AuthProvider
    ├── EditorModeProvider
    ├── NotifyProvider
    ├── UiSettingsProvider
    └── QuotaProvider
        ├── PersistentBackground
        ├── глобальные уведомления
        └── RootShell
            ├── AppShell / PublicShell
            │   ├── AppHeader
            │   ├── DesktopSidebar
            │   ├── MobileNavigation
            │   ├── AdminNavigation
            │   └── PageContent
            │       └── Outlet
            └── текущая страница
```

Маршрут меняет только содержимое `<Outlet />`. Постоянная оболочка больше не принадлежит странице.

Созданы и используются:

```text
app/
├── AppShell.jsx
├── PublicShell.jsx
├── RootShell.jsx
├── AppProviders.jsx
└── PageMeta.jsx

components/shell/
├── PersistentBackground.jsx
├── AppHeader.jsx
├── DesktopSidebar.jsx
├── MobileNavigation.jsx
├── AdminNavigation.jsx
├── PageContent.jsx
├── RouteErrorBoundary.jsx
└── navigation.js

contexts/
├── UiSettingsContext.jsx
└── QuotaContext.jsx
```

CT-фронтенд также переведён с собственного `Layout` внутри каждой страницы на один постоянный `AppShell`.

## Что теперь сохраняется при навигации

При переходе между страницами не перемонтируются:

- Canvas и WebGL-контекст фонового эффекта;
- текущая позиция анимации;
- случайно выбранный вариант фона;
- данные энергии задач и рейтинга;
- время следующего восстановления энергии;
- глобальные providers;
- глобальные уведомления;
- шапка;
- левое меню;
- слушатели темы и настроек.

Обновляться имеют право только части, которые действительно зависят от маршрута:

- активный пункт меню;
- подпись текущего раздела;
- метаданные страницы;
- центральное содержимое `<Outlet />`;
- route-level loading/error для впервые загружаемого чанка.

## Энергия

`QuotaProvider` теперь существует один раз на авторизованную сессию и не очищает старые данные во время фонового обновления.

Дополнительно:

- энергия задач и энергия рейтинга разделены на независимые контексты;
- обновление одной энергии не обязано перерисовывать потребителей другой;
- неизменившиеся bucket-объекты сохраняют прежние ссылки;
- несколько параллельных refresh-запросов объединяются в один;
- запоздавший ответ от предыдущей авторизованной сессии игнорируется и не может показать квоту другого пользователя после logout/login;
- данные повторно синхронизируются после focus, online, pageshow и возвращения во вкладку;
- восстановление по серверному времени запускает точечный refresh;
- если запрос на границе восстановления временно не прошёл, provider повторяет только этот refresh с паузой, не очищая показанные значения;
- секундный отсчёт вынесен в один общий `useSyncExternalStore`, а не создаёт отдельный interval для каждого виджета;
- раз в секунду обновляются только маленькие компоненты таймера, а не всё приложение.

## Настройки интерфейса

Один широкий контекст настроек дополнительно разделён на домены:

- тема;
- фон;
- редактор;
- навигация.

Поэтому изменение вида редактора не уведомляет WebGL-фон, а сворачивание бокового меню не заставляет Monaco обновлять тему.

`PersistentBackground` подписан только на параметры фона и палитры. Обычный переход по маршруту для него вообще не является изменением.

Загрузка настроек аккаунта также перенесена из `AuthContext` в долгоживущий `UiSettingsProvider`. Теперь аутентификация отвечает только за сессию и профиль, а настройки интерфейса имеют собственный lifecycle. Обновление access-токена раз в десять минут не запускает повторную инициализацию темы или WebGL-сцены.

Страница настроек больше не управляет оболочкой через собственную запись в `localStorage` и ручное глобальное событие. Предпросмотр изменений идёт через `useUiSettingsActions`, а provider уже сам обновляет узкие контексты и совместимый локальный snapshot.

## Страница решения задания

Для задания добавлены отдельные границы рендера:

- `CodeEditor` мемоизирован;
- Monaco больше не имеет `key`, зависящего от ID задания или языка;
- смена ID в том же маршруте переключает именованную Monaco-модель через `path`, но сохраняет сам editor instance вместо его уничтожения;
- история undo, позиция и модель больше не смешиваются между разными заданиями;
- старое задание не очищается во время загрузки следующего, поэтому рабочая область не схлопывается в полный skeleton;
- шапка задания с кнопками вынесена в `AssignmentSolveHeader` и мемоизирована;
- нижняя панель действий вынесена в `SolveActionDock` и мемоизирована;
- отправка решения проксируется через стабильный event-callback, поэтому нижняя панель не получает новую функцию на каждый введённый символ;
- иконка действия передаётся как стабильный тип компонента, а не как новый JSX-объект на каждом render;
- `StatementViewer` мемоизирован;
- параметры и обработчики Monaco стабилизированы через `useMemo`/`useCallback`;
- смена палитры обновляет тему существующего Monaco, не перезапуская загрузчик редактора.

Важно: React всё равно может повторно вызвать функцию родительского компонента. Это нормально. Главное исправление — дорогие части больше не перемонтируются и не теряют внутреннее состояние.

## Code splitting

Страницы основного и CT-фронтенда загружаются через `React.lazy`. Первое открытие нового раздела может показать skeleton только в центральной области. Шапка, фон, энергия и навигация остаются на месте.

## Защита архитектуры от отката

В оба фронтенда добавлены build-time проверки:

- старый `Layout.jsx` не может вернуться;
- страницы не могут снова импортировать layout;
- `QuotaProvider` должен находиться только в `AppProviders`;
- `BgFxCanvas` должен принадлежать только `PersistentBackground`;
- `CodeEditor` нельзя снова привязать `key` к заданию;
- фон не может снова зависеть от старого `uiRev`;
- route-level lazy loading и постоянный shell обязательны;
- quota bucket-контексты должны оставаться раздельными;
- фон и редактор должны использовать узкие контексты настроек.

Проверки запускаются через `prestart` и `prebuild`.

# Что во фронтенде всё ещё не идеально

## 1. Крупные feature-компоненты

Самые тяжёлые файлы всё ещё объединяют загрузку данных, бизнес-логику, анимации и представление:

- `AssignmentSolvePage.jsx` — около 2,5 тыс. строк;
- `CourseAssignmentsPage.jsx` — около 2 тыс. строк;
- `SettingsPage.jsx` — около 1,7 тыс. строк;
- `AgentPage.jsx` — около 1,6 тыс. строк;
- `AssignmentEditPage.jsx` — около 1,4 тыс. строк;
- `AdminSolutionsPage.jsx` — более 1,1 тыс. строк;
- `AdminAnalyticsPage.jsx` — около 900 строк.

Следующий правильный этап — feature-папки с `hooks`, `reducers`, `api`, `views` и небольшими memo-компонентами. Делать массовую механическую нарезку без тестов опасно: можно разнести связанную бизнес-логику и получить скрытые ошибки.

## 2. Код задания всё ещё хранится в родителе

Monaco уже не перемонтируется, а статические дочерние блоки пропускают лишние render через `React.memo`. Но значение `code` пока хранится в `AssignmentSolvePage`, поэтому сама большая render-функция вызывается при вводе символов.

Идеальный следующий шаг для этой страницы:

```text
AssignmentSolveFeature
├── AssignmentDataProvider
├── DraftStore (useSyncExternalStore или reducer)
├── CodeWorkspace
├── StatementPanel
├── TestsPanel
├── ResultPanel
└── ActionDock
```

Тогда на каждый символ будут обновляться только Monaco, статус черновика и кнопки, которым действительно нужен код. Это требует отдельного функционального прохода и runtime-тестов отправки решений.

## 3. Нет общего кэша серверных данных

Многие страницы всё ещё используют собственные `useEffect + loading + error`. Нет общей системы, которая даёт:

- дедупликацию запросов;
- отмену устаревших запросов;
- stale-while-revalidate;
- сохранение данных при возврате на страницу;
- единые retry/error-policy.

Нужен проектный query-layer (например, TanStack Query либо собственный небольшой store поверх текущего API-клиента).

## 4. Не нужен общий keep-alive для всех страниц

Оставлять в памяти каждую когда-либо открытую страницу — не идеальная оптимизация. Это сохраняло бы устаревшие подписки, таймеры, большие таблицы и редакторы.

Правильный подход:

- shell и глобальные данные живут постоянно;
- обычные страницы размонтируются при уходе;
- только дорогие рабочие пространства получают явное сохранение черновика/сессии;
- данные страниц сохраняются query-кэшем, а не скрытым DOM.

## 5. Дублирование между `web` и `web-ct`

Оба фронтенда всё ещё имеют отдельные реализации auth, HTTP-клиента, ролей и части синхронизации настроек. Их стоит вынести в общий workspace-package, чтобы исправления не копировались вручную.

## 6. Слишком глобальный CSS

Оболочка уже компонентная, но стили по-прежнему лежат в больших глобальных файлах. Нужны feature-scoped CSS Modules или другой scoped-подход, иначе одна правка селектора может задеть несвязанную страницу.

## 7. Нет полноценных frontend-тестов

Build-time инварианты ловят архитектурный откат, но не заменяют:

- component tests;
- route tests;
- browser/E2E tests;
- тест сохранения WebGL-контекста;
- тест непрерывности энергии;
- тест сохранения Monaco при смене задания;
- тест мобильного меню.

## 8. Фоновые движки всё ещё слишком большие

`BgFxCanvas`, `BgFxNeuralWebgl` и `BgFxSolarWebgl` стали правильно жить в приложении, но сами renderer-модули остаются крупными и императивными. Позже стоит вынести общий lifecycle и рассмотреть `OffscreenCanvas`/worker для тяжёлых эффектов.

## 9. Начальный auth-bootstrap

При первом открытии приложения refresh-сессии всё ещё асинхронный. Shell уже не перемонтируется на обычных маршрутах, но для полностью бесшовного первого кадра можно добавить отдельное boot-состояние с восстановлением последней известной сессии.

## Рекомендуемый следующий порядок

1. Добавить React/E2E-тесты на постоянный shell, энергию и Monaco.
2. Вынести draft/code state задания в отдельный feature-store.
3. Ввести общий query cache.
4. Разделить `AssignmentSolvePage`, затем `CourseAssignmentsPage` и `SettingsPage`.
5. Вынести общую платформенную часть `web` и `web-ct` в package.
6. Локализовать CSS и renderer lifecycle.
